## 1. 核心业务对象与关系

系统以项目作为业务执行和经营管理的核心载体，将客户、合作对象、合同、结算、发票、应收应付和收付款持续关联到具体项目。

整体业务关系可以概括为：

客户 → 项目 → 业务执行 → 合同与结算 → 发票与应收应付 → 收付款 → 项目经营结果

项目内部同时存在方案、达人合作、内容交付、预算及其他业务记录，共同描述项目从启动到最终完成的全过程。

客户与项目

客户是项目的业务来源。一个客户可以对应多个项目，每个项目独立记录执行过程、预算、收入、成本、合同、结算及经营结果。

项目是经营数据归集的主要单位。与项目有关的合作、收入、成本、应收应付和资金事项最终都需要能够追溯到对应项目。

达人、账号与结算主体

达人代表实际合作对象，达人账号代表其在不同内容平台上的具体业务身份。

同一个达人可以拥有多个平台账号，不同项目合作时需要明确实际使用的账号及平台。

实际收款方可能是达人本人、MCN、代理公司或其他结算主体，因此达人、达人账号和结算主体分别管理，并在具体合作中建立关系。

合同与结算

合同记录双方已经约定的商业条件，结算记录实际需要收取或支付的金额及时间节点。

一个合同可以对应多个结算节点，同一项目也可以存在多个客户侧和成本侧合同。

每一笔实际收款或付款义务独立形成结算记录，并继续关联对应的发票、应收应付和实际收付款。

因此：

业务合作 → 合同约定 → 结算义务 → 发票 → 应收 / 应付 → 实际收付款

原始合同、发票、报价及其他文件作为业务依据，与对应的结构化业务记录保持关联。

## 2. 项目与业务状态逻辑

项目状态反映项目当前所处的主要业务阶段，并随着实际业务事实持续更新。

项目主流程为：

项目创建 → 方案制作 → 客户确认 → 合同签署 → 达人执行 → 内容审核 → 发布 → 客户验收 → 结算 → 完成

项目状态由实际业务进展决定。例如，方案获得客户确认后进入后续合同及执行阶段；达人合作确认并开始执行后进入达人执行阶段；内容发布并完成客户验收后，业务履约进入完成阶段；后续继续跟踪结算、开票、回款和付款。

达人合作状态

达人合作拥有独立于项目主状态的执行流程：

候选 → 已联系 → 报价中 → 谈判中 → 已确认 → 制作中 → 待发布 → 已发布 → 待结算 → 已结算

一个项目可以同时存在多个达人，每个达人分别推进自己的合作状态。

因此项目处于“达人执行”阶段时，不代表所有达人处于完全相同的状态。系统通过每一条达人合作记录保存具体执行进度，再汇总形成项目整体状态。

项目关闭

项目完成同时考虑业务履约和财务结算。

业务关闭（Business Closed）

项目约定的业务交付已经完成，内容已经发布并完成客户验收，相关业务履约事项已经结束。

财务关闭（Financial Closed）

客户侧销售发票及应收回款已经完成，成本侧进项发票、应付款及相关报销已经处理完成。

只有业务和财务均完成关闭后，项目才进入最终完成状态：

Project Completed = Business Closed + Financial Closed

因此，一个已经完成交付和客户验收、但仍存在未收客户款项的项目，业务上已经完成，经营管理上仍需要继续跟踪。

## 3. 合作、合同与结算逻辑

项目执行过程中产生的商业约定通过合作、合同和结算记录逐步形成可管理的收付款义务。

客户侧

客户侧主要形成收入及收款关系：

客户项目 → 客户合同 → 收款节点 → 销售发票 → 应收 → 实际收款

客户合同可以约定一次或多次收款。

例如，一个项目可以约定签约后收取 50%，项目验收后收取剩余 50%。系统分别记录两个收款节点，并独立跟踪对应的开票、应收和收款情况。

成本侧

成本侧根据实际业务合作形成付款关系：

达人 / 平台 / 供应商合作 → 合同或合作约定 → 成本结算 → 进项发票 → 应付 → 实际付款

每一笔成本按照实际结算对象形成独立的结算记录。

例如，一次达人合作中：

达人合作费用 ¥8,000  
平台服务费 ¥400

如果 ¥8,000 支付给达人或其结算主体，而 ¥400 支付给平台，则形成两笔独立结算义务。

这样可以分别管理合同依据、发票、应付和付款状态，同时保留两笔成本与同一项目、同一次达人合作之间的关系。

结算记录

结算记录是业务合作与财务处理之间的连接点。

每一条结算记录至少需要明确：

结算所属项目  
业务来源  
收款或付款对象  
结算金额  
预计结算时间  
对应合同或合作依据  
发票状态  
应收或应付状态

实际收付款状态

通过结算记录，项目执行过程中形成的商业约定能够继续进入后续财务运营。

## 4. 收入、成本与利润逻辑

经营结果按照统一的管理口径形成，使不同项目之间能够进行一致的利润分析。

收入

项目收入按照业务履约情况确认。

当前经营口径下，项目完成相应业务交付并获得客户验收后确认收入。

合同金额和客户付款进度分别用于描述商业约定和现金回收情况，不直接替代收入确认。

因此：

合同签署 ≠ 收入确认

收入确认 ≠ 已经收到现金

系统分别管理合同、收入、应收和实际收款，使项目盈利情况与资金情况能够独立观察。

成本

项目成本按照实际业务承担情况归集。

主要包括：

外部执行成本

达人费用、平台服务费、供应商费用及其他直接由外部合作产生的项目成本。

公司承担成本

由公司承担并能够直接归属于项目的费用，例如项目相关差旅、采购、报销及其他执行费用。

公共费用分摊

无法直接归属于单一项目的公司公共费用，根据确定的分摊规则进入各项目。

成本是否进入项目经营结果，根据已经确认的业务事实及实际结算义务判断。

达人处于询价或谈判阶段时，报价可以用于业务决策和预算判断；合作确认并形成实际结算义务后，相应成本进入正式成本管理。

同样，尚未经过确认的报销申请不会直接改变正式项目利润。

项目利润

当前项目利润采用以下经营口径：

项目利润 = Net Revenue + Retained Rebate - External Execution Cost - Company-Borne Cost - Allocated Overhead

其中：

Net Revenue 为项目确认的净收入。

Retained Rebate 为按照业务规则由公司保留并计入项目经营结果的返点。

External Execution Cost 为达人、平台、供应商等外部合作形成的项目执行成本。

Company-Borne Cost 为公司直接承担并归属于该项目的费用。

Allocated Overhead 为按照既定规则分摊至项目的公共费用。

通过统一利润口径，项目能够在相同基础上进行利润分析，并进一步汇总形成客户及公司层面的经营结果。

## 5. 预算与费用分摊逻辑

预算用于管理项目预计投入及执行过程中的资源使用情况。

预算版本

项目创建后建立初始预算。

预算发生正式调整时，不直接覆盖原预算，而是形成新的预算版本：

初始预算 → 预算调整 → 审批确认 → 新预算版本

系统以最新已批准的预算版本作为当前有效预算，同时保留历史版本及调整记录。

这样可以持续追踪：

原始预算  
预算调整  
当前预算  
已用预算  
剩余预算

预算使用率

其中：

剩余预算 = 当前有效预算 - 已用预算

预算使用率 = 已用预算 ÷ 当前有效预算

预算调整不会改变已经发生的实际成本，只改变当前用于项目管理和预算控制的预算基准。

公共费用分摊

能够明确归属于单个项目的成本直接进入对应项目。

无法直接归属于某个项目、但属于公司整体经营成本的公共费用进入公共费用池，再按照既定分摊规则分配至项目。

整体逻辑为：

公司公共费用 → 确定分摊范围与规则 → 分配至项目 → 进入项目完整经营成本

分摊规则可以根据企业实际管理需求采用收入、项目规模、人员投入或其他合理的业务驱动因素。

系统保留原始公共费用、分摊规则和项目分摊结果，使项目完整利润能够同时反映直接执行成本和公司共同资源投入。

## 6. 应收应付与资金逻辑

系统将项目经营结果与实际资金流动分别管理，并通过应收应付和收付款记录建立连接。

应收

客户合同及结算安排形成收款节点。

达到相应业务条件后形成应收，并持续跟踪：

收款约定 → 应收形成 → 销售发票 → 到期 → 实际收款

每笔应收记录预计收款日期、应收金额、发票及实际收款情况。

超过预计收款日期仍未完成收款的应收进入逾期状态，供管理层持续跟踪。

应付

达人、平台、供应商及其他成本合作形成付款义务。

系统持续跟踪：

成本结算 → 应付形成 → 进项发票 → 到期 → 实际付款

每笔应付保留项目、合作对象及结算来源，使实际付款能够继续追溯至产生该成本的具体业务事项。

收付款匹配

银行流水进入系统后，与已有应收应付进行匹配。

处理过程为：

银行流水 → 系统匹配 → 人工确认 → 更新应收应付及收付款状态

一笔实际收付款确认后，对应的应收或应付余额及状态同步更新。

现金流预测

未来现金流基于已经形成的收付款安排进行预测。

预计收款来自项目应收及其预计收款日期。

预计付款来自项目应付及其预计付款日期。

系统按照时间汇总未来资金流入和流出，并结合期初资金形成现金流预测：

期初资金 + 预计收款 - 预计付款 = 预计期末资金

管理层因此可以同时观察项目利润、应收回款和未来资金情况。

## 7. 业务事实、确认与追溯

系统中的正式业务状态和经营数据建立在经过人工确认的业务事实之上。

自然语言、语音、聊天记录、合同、发票、Excel 和其他文件提供业务信息及原始依据。AI 可以识别其中的业务事实、整理信息并提出相应的数据更新。

业务人员对 AI 整理结果进行检查、修改和确认。人工确认后，相应内容成为正式业务事实，并按照既定业务规则更新项目、合作、合同、结算及财务记录。

因此整体形成：

原始业务信息 → AI 识别与整理 → 人工确认 → 正式业务事实 → 业务规则处理 → 经营结果

正式数据同时保留与原始业务依据及相关业务记录之间的关系。

当管理层看到一个项目的利润、预算使用、应收回款或现金流结果时，可以继续向下追溯至对应的收入、成本、结算、合同、合作及原始资料。

系统同时记录关键业务事实的变化过程，包括状态变化、修改内容、操作人员、确认时间及相关业务依据，使经营结果能够解释其形成过程。

最终形成：

经营结果 → 财务记录 → 结算与合同 → 业务执行 → 原始业务依据
